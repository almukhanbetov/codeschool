# CodeSchool.kz — исправление подключения Flutter к VPS и сборка APK

Работа с существующим Flutter-приложением в папке `flutter`. Проблема:
«Сервермен байланыс жоқ» (нет связи с сервером) при открытии каталога на
реальном Android-телефоне.

## 1. Аудит подключения

Проверены все места, где приложение знает о сети:

| Файл | Что проверено |
|---|---|
| `lib/core/config/app_env.dart` | `AppEnv.resolve()` — `API_BASE_URL`/`APP_FLAVOR` через `String.fromEnvironment`, dev-дефолт `http://10.0.2.2:8080/api/v1` (эмуляторный алиас), prod-дефолт `https://api.codeschool.kz/api/v1` |
| `lib/core/network/api_client.dart` | `Dio(BaseOptions(baseUrl: env.apiBaseUrl, ...))`, обработка `DioException` (timeout → `ApiException.timeout()`, всё остальное → `ApiException.network()`) |
| `lib/core/network/api_exception.dart` | Маппинг статусов 401/403/404 на `isUnauthorized`/`isForbidden`/`isNotFound` — уже корректен, не менялся |
| `android/app/src/{main,debug,profile}/AndroidManifest.xml` | **см. §1.1 — здесь и была настоящая причина** |
| `android/app/build.gradle.kts` | `signingConfig` релиза — см. §5 |
| Использование localhost/127.0.0.1/10.0.2.2 | Только внутри `_devDefault` (намеренно, для эмулятора) — в prod-пути не встречается |

### 1.1 Настоящая причина — не URL, а разрешение Android

**`android/app/src/main/AndroidManifest.xml` не содержал
`<uses-permission android:name="android.permission.INTERNET"/>`.**

Это главный манифест — единственный, который попадает в **release**-сборку.
У `debug`- и `profile`-вариантов есть свои оверлей-манифесты
(`android/app/src/debug/AndroidManifest.xml`,
`android/app/src/profile/AndroidManifest.xml`), и в них разрешение INTERNET
**уже есть** — оно добавляется туда автоматически инструментами Flutter для
хот-релоуда/VM service, а не самим разработчиком. Из-за этого:

- `flutter run` / debug-сборка — работала (INTERNET есть из debug-оверлея);
- `flutter build apk --release` — **не могла обратиться ни к одному хосту
  вообще**, независимо от того, какой URL сконфигурирован.

Без разрешения INTERNET каждый запрос падает на уровне сокета **до** DNS и
TLS. `ApiClient` перехватывает такой `DioException` (тип не
timeout/connectionTimeout) и мапит его в `ApiException.network()` — именно
тот код, что превращается в строку `error.network`
(`lib/core/l10n/translations_kz.dart:382` = `'Сервермен байланыс жоқ'`).
Это объясняет симптом дословно, включая казахский язык интерфейса — не
DNS, не TLS, не HTTP-статус, не таймаут, а полное отсутствие сетевого
доступа у процесса.

Проверено: `flutter build apk --release --dart-define=API_BASE_URL=https://api.codeschool.kz/api/v1`
**до** исправления манифеста собирал APK без единой ошибки (компилятор не
может обнаружить отсутствие Android-разрешения) — баг был невидим на этапе
сборки и проявлялся только при реальном запросе с телефона.

### 1.2 Второй потенциальный источник той же ошибки (не баг, а риск использования)

Если release-сборку когда-либо собрать **без** `--dart-define=API_BASE_URL=...`,
`AppEnv.resolve()` по умолчанию использует `_devDefault` =
`http://10.0.2.2:8080/api/v1` — адрес, работающий только внутри Android-
эмулятора. На реальном телефоне (не эмуляторе) такой адрес ничего не
резолвит и даёт тот же `ApiException.network()`. Код это уже документирует и
поддерживает разделение окружений так, как просит бриф (см. §3) — исправлять
тут нечего, важно не забывать передавать флаг при сборке релиза, что и
проверено (§5).

## 2. Production API — PASS

Проверены реальные маршруты по исходникам бэкенда
(`backend/internal/courses/routes.go`) и вживую по production:

| Endpoint | Метод в бэкенде | Проверено | Результат |
|---|---|---|---|
| `GET /courses` | `h.List` | curl, HTTPS | `200 OK`, 1 курс (`codeschool-year1-logic`, id=1, 72 урока) |
| `GET /courses/slug/codeschool-year1-logic` | `h.GetBySlug` | curl, HTTPS | `200 OK` |
| `GET /courses/1/content` (id, не slug) | `h.GetContent` (принимает только числовой `:id`, `httpx.ParseIDParam`) | curl, HTTPS | `200 OK`, **9 модулей, 72 урока** |

**Уточнение по брифу:** `GET /courses/codeschool-year1-logic/content` (третий
эндпоинт из задания дословно) на бэкенде возвращает `400` — `GetContent`
принимает только числовой `:id`, не slug. Это не ошибка бэкенда и не то, что
нужно чинить: реальный маршрут получения контента по slug — сначала
`GET /courses/slug/:slug` (получить `id`), затем `GET /courses/:id/content`,
именно так уже реализовано в `CatalogRepository`
(`getBySlug()` → в screens используется числовой `courseId`, contentProvider
всегда вызывается с уже известным `id`). Флаттер-приложение никогда не
обращается к content по slug напрямую, поэтому кода менять не пришлось —
только подтвердить маршрут curl'ом (см. лог выше).

- **TLS**: сертификат Let's Encrypt для `api.codeschool.kz`, валиден до
  16.12.2026, проверка стандартная (не отключалась, не добавлялось
  исключений/trust-anchors).
- **DNS**: `api.codeschool.kz` → `89.207.254.215`.
- **HTTP**: `200` за ~150 мс.
- Дублирования `/api/v1` в URL не обнаружено: `Dio.baseUrl` = `.../api/v1`
  (без хвостового слэша), пути репозиториев начинаются с `/`
  (`/courses`, `/auth/login`, ...) — конкатенация Dio даёт корректный URL.
  Убедился дополнительно через `strings` на собранном release APK (см. §5) —
  внутри ровно `api.codeschool.kz/api/v1`, без повторов.

## 3. Разделение окружений — PASS (уже было реализовано, не менялось)

`AppEnv` (Stage 35: описано в собственном доко-комментарии файла) уже
реализует ровно то, что просит бриф:

- Development — `http://10.0.2.2:8080/api/v1` (дефолт без флагов, для
  локального docker-compose backend через эмуляторный алиас).
- Production — `https://api.codeschool.kz/api/v1`, задаётся явно через
  `--dart-define=API_BASE_URL=...` (см. точную команду в §5) либо через
  `--dart-define=APP_FLAVOR=prod`.
- Токены/секреты в `--dart-define` не передаются и не хранятся — только сам
  URL (не секрет, тот же адрес публично виден в браузере на codeschool.kz).
- Ничего дополнительно не потребовалось реализовывать — только собрать с
  правильным флагом (что и было причиной §1.2, если флаг забыть).

## 4. Проверка на Android — PASS

Телефон: `M2102J20SG`, Android 12, `adb` id `4622f67a` (тот же, что и в
предыдущей стадии).

Подготовка: `adb uninstall` старой debug-сборки (во избежание конфликта
подписи), `adb reverse --remove-all` (release-сборка идёт по реальной сети,
не через локальный туннель), `flutter build apk --release
--dart-define=API_BASE_URL=https://api.codeschool.kz/api/v1`, `adb install -r`,
`pm clear` для чистого состояния, запуск.

| Проверка | Результат |

### Диагностические логи

`adb logcat`, отфильтровано от паролей/токенов. В release-сборке
`LogInterceptor` в `ApiClient` активен только под `kDebugMode`
(`lib/core/network/api_client.dart`), поэтому в релизе тела запросов/ответов
в лог не пишутся вовсе — сработало по дизайну, ничего чувствительного не
залогировано и не требовалось скрывать дополнительно.

## 5. Сборка APK

```
flutter analyze                                                              → No issues found!
flutter test                                                                 → 00:27 +125: All tests passed! (125/125)
flutter build apk --release --dart-define=API_BASE_URL=https://api.codeschool.kz/api/v1
                                                                              → ✓ Built build/app/outputs/flutter-apk/app-release.apk
```

**Путь к APK:** `flutter/build/app/outputs/flutter-apk/app-release.apk`
**Размер:** 60 251 651 байт (≈ 57.5 MiB / 60.3 MB)

Проверено `strings` по собранному бинарнику: внутри присутствует
`api.codeschool.kz/api/v1`, **не найдено** ни одного вхождения `10.0.2.2:8080`
— production-сборка не может случайно обратиться к dev-адресу.

**Подпись:** `android/app/build.gradle.kts` — релизный `buildTypes.release`
использует `signingConfig = signingConfigs.getByName("debug")` (штатный
шаблон Flutter, TODO-комментарий в файле не менялся, конфигурация подписи не
трогалась по требованию брифа). **Это debug-подпись — собранный APK пригоден
только для тестирования (в т.ч. установки на этот телефон через `adb`), не
для публикации в Google Play.** Для публикации потребуется отдельный
`signingConfig` с release-ключом — вне рамок этой задачи.

Установка на устройство и проверка каталога через реальный VPS — выполнены
(§4), результат PASS.

## 6. Изменённые файлы

- `android/app/src/main/AndroidManifest.xml` — добавлено
  `<uses-permission android:name="android.permission.INTERNET"/>` в главный
  манифест (корень проблемы, §1.1).
- `test/android/release_manifest_test.dart` — новый регрессионный тест:
  читает главный манифест и проверяет наличие разрешения INTERNET, чтобы эта
  ошибка не могла повториться незаметно.
- `test/core/config/app_env_test.dart` — новый тест: без `--dart-define`
  `AppEnv` резолвится в dev-дефолт, никогда не в production по умолчанию.
  Prod-путь (`--dart-define=APP_FLAVOR=prod`) и корректность самого
  production-URL проверены отдельным запуском `flutter test
  --dart-define=APP_FLAVOR=prod` (см. вывод ниже) — не оставлены как
  постоянный тест в основном наборе, поскольку `String.fromEnvironment`
  фиксируется на этапе компиляции самого тестового бинарника, а не в
  рантайме, и обычный `flutter test` (без флагов) не может держать оба пути
  одновременно.

```
$ flutter test test/core/config/app_env_test.dart --dart-define=APP_FLAVOR=prod
Expected: dev
  Actual: prod          ← подтверждает, что флаг реально переключает flavor
```

## 8. Оставшиеся проблемы / ограничения

1. **Release-APK подписан debug-ключом** (существующая конфигурация,
   осознанно не менялась) — годится только для тестовой установки, не для
   Google Play. Нужен отдельный `signingConfig` с производственным ключом —
   отдельная задача, требующая генерации/хранения секретного ключа.
2. Полный сценарий «вход под реальным паролем → просмотр личного прогресса на
   production» не выполнялся намеренно — потребовал бы либо существующих
   продовых учётных данных (не переданы в задаче), либо регистрации нового
   аккаунта в production PostgreSQL, что прямо запрещено формулировкой брифа
   («не изменяй production PostgreSQL и существующие данные пользователей»).
   401-путь (неверные данные) проверен полностью и достаточен для
   подтверждения, что сама авторизация технически достучивается до
   production и корректно обрабатывает ответ.
3. APK не проверялся на других версиях Android/устройствах — только на
   подключённом `M2102J20SG` (Android 12).
